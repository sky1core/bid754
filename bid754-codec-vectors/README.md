# BID Codec Cross-Language Test Vectors

This README explains how to consume the current generated artifact. The
normative codec API and vector-protocol contract is
`docs/BID_CODEC_SPEC.md`; when prose here conflicts with that specification,
the specification wins. Current records and counts come from generated files
and verification anchors, not from this README.

## Usage

### Generate vectors
```bash
make generate-testspec
```

`vectors.json` is generated through the `bid_codec_vectors` configuration in `devtools/testgen_manifest.json`. Do not edit this file directly.

### Verify in each language
Read `vectors.json` and:
1. `hex` → decode → compare Components with the vector's `sign/coefficient/exponent/kind/payload`
2. decode result → `toString` → compare with `decimal_string`
3. `decimal_string` → `fromString` → encode → compare with `encoded_hex`/`encoded_hi`
4. if canonical: Components → encode → compare with `encoded_hex` (bit roundtrip)
5. verify that invalid byte length fails through each language's error mechanism
6. verify every `reject_vectors` row fails: a `from_string` row must fail the parse,
   an `encode` row must be rejected by the width's encode, and a `to_string` row
   must be rejected before rendering — in all cases through the
   language's error mechanism, never by silent truncate/clamp/mask or panic/trap; a
   consumer whose `Components` field types cannot construct a row's `requires`
   capability skips it and reports the skip instead of silently passing
7. verify every `string_vectors` row succeeds: `fromString(input)` must parse without
   error and `toString` of the result must equal `expected` byte-for-byte; then the
   closure leg — `fromString(expected)` must itself parse without error and its
   `toString` must reproduce `expected` exactly (renderings are reparseable fixed
   points); every consumer consumes every row (the channel is capability-ungated)
   and reports the consumed count

## Vector format

The top-level file is
`{"format_version": 5, "vectors": [...], "reject_vectors": [...], "string_vectors": [...]}`.
Every consumer fails on `format_version != 5` as an explicit error.

```json
{
  "type": "bid64",
  "hex": "31c0000000000001",
  "sign": false,
  "coefficient": "1",
  "exponent": 0,
  "kind": "normal",
  "decimal_string": "+1E+0",
  "canonical": true,
  "encoded_hex": "31c0000000000001"
}
```

| Field | Description |
|------|------|
| type | "bid32", "bid64", "bid128" |
| hex | input BID value (hex string, little-endian word order for bid128) |
| hex_hi | bid128 high word (bid128 only) |
| sign | true=negative |
| coefficient | significand (decimal string, "" for special values) |
| exponent | power of 10 |
| kind | "normal", "zero", "inf", "qnan", "snan" |
| payload | NaN payload as a decimal string (the full BID128 110-bit value, so payloads at or above 2^64 are expressible; present only when non-zero) |
| decimal_string | shared BID codec string representation. Every language verifies it with `toString`/`fromString` |
| canonical | if true, encoding the decoded Components must reproduce the input words exactly |
| encoded_hex | encode result (same as hex if canonical) |
| encoded_hi | high word of the bid128 encode result |

Each language's consumer uses the same row to verify bit decode/encode, string
render/parse, and little-endian bytes decode/encode. BID32/64/128 bytes decode
input must be exactly 4/8/16 bytes respectively.

Each language's consumer also verifies the shared failure semantics through the
`reject_vectors` array (no hand-maintained per-language failure lists). The
`fromString` grammar is the strict ASCII grammar defined in
`docs/BID_CODEC_SPEC.md`: the whole input must be ASCII, digits are ASCII
`0`-`9` only, no underscores, no whitespace inside the token, no sign inside a
NaN payload, the exponent literal must be below the shared exact-integer bound
`2^53` in magnitude (the widest bound every consumer's number type can check
exactly; a literal at or beyond it is rejected through the same error channel
in every language) with only the
fraction-adjusted final exponent required to fit a signed 32-bit integer (so
every `toString` rendering reparses — round-trip closure), the payload value
must be below the schema-wide NaN
payload limit `10^33`, and the coefficient value must not exceed the schema-wide
maximum `10^34-1`. A language
whose bytes decode API takes a dynamic byte buffer must report invalid length
as a failure. The Rust fixed-array bytes API enforces length through the type,
and the dynamic slice failure check is verified with `try_decode*_bytes`.

`Encode*` and `toString` vector verification cover both sides of their
validating component contracts. Canonical `vectors` rows pin the success side:
in-range `Components`
must encode to the exact expected bits. `reject_vectors` `encode` rows pin the
rejection side: a `Components` value with an out-of-range or out-of-domain
field must fail through the language-specific error mechanism — silent
truncate/clamp/mask and panic/trap are both rejected (see the encode reject
contract in `docs/BID_CODEC_SPEC.md`). `reject_vectors` `to_string` rows
pin the width-independent schema: a renderer must reject any field that the
selected kind would discard, a normal coefficient outside `1..10^34-1`, or a
NaN payload outside `0..10^33-1`. It must not emit a string that reparses to a
different kind or component value.

## Reject vector format

`reject_vectors` rows share the `Components` field encodings with `vectors`
rows (zero-value fields are omitted):

```json
{"channel": "encode", "type": "bid32", "kind": "normal",
 "coefficient": "10000000", "reason": "coefficient_overflow"}
{"channel": "to_string", "kind": "inf", "coefficient": "1",
 "reason": "coefficient_not_representable_for_infinity"}
{"channel": "from_string", "input": "1E1_0", "reason": "underscore"}
```

| Field | Description |
|------|------|
| channel | "from_string" (malformed input string), "encode" (invalid width-specific `Components`), or "to_string" (invalid/lossy width-independent `Components`) |
| type | BID width under test ("encode" channel only; `from_string` and `to_string` rows are width-independent) |
| input | exact input string ("from_string" channel only) |
| sign/kind/coefficient/exponent/payload | the `Components` value to encode or render ("encode"/"to_string" channels) |
| reason | tag naming the violated boundary (e.g. "coefficient_overflow", "exponent_out_of_range", "payload_overflow", "nan_payload_exceeds_schema_max", "non_ascii", "underscore") |
| requires | capability tag when the row is only constructible in languages whose field types can express it ("bignum_coefficient", "negative_coefficient", "negative_payload"); consumers without the capability skip and report |

Field-domain cases that this shared schema cannot express (a non-boolean
`sign`, a wrong coefficient/exponent/payload numeric type including boolean-as-integer
coercion, an out-of-int32/non-finite
`exponent`, or an unrecognized `kind`) are emitted by the same generator directly
into the per-language harnesses of the languages that can construct them.

The `from_string` rows include machine-integer accumulation-overflow probes
(a 40-digit coefficient literal `10^39` above the `u128` maximum, a 25-digit
exponent literal beyond both the `i64` accumulator range and the shared `2^53`
literal bound, a 40-digit NaN payload literal) plus the `2^53` exponent-literal
bound one-at-the-edge in both signs, so fixed-width checked accumulation and
big-integer schema caps and the explicit `2^53` literal bound are all pinned
to fail the same inputs through the same error channel.

## String vector format (success channel)

`string_vectors` rows pin the string surface from the success side:

```json
{"input": "12E+2147483647", "expected": "+1.2E+2147483648"}
```

| Field | Description |
|------|------|
| input | exact `fromString` input; parsing must succeed in every language |
| expected | exact `toString` rendering of the parsed `Components`; must match byte-for-byte, and must itself reparse through `fromString` and re-render identically (closure leg) |

The channel covers what the other two channels cannot: contract-valid parses
whose `Components` no BID width encodes — above all int32-extreme exponents,
where a `toString` that computes the adjusted exponent (`exponent + digits - 1`)
in 32-bit arithmetic silently wraps the rendered sign — plus the successful
grammar-edge normalizations (surrounding ASCII whitespace trim, empty
integer/fraction sides, leading-zero collapse, NaN payload leading-zero
normalization, case-insensitive special tokens). Rows are capability-ungated
pure ASCII string pairs: every consumer (the six required languages plus the
`bid754-rs` full-library consumer) consumes every row and reports the consumed
count. Totals are pinned in `devtools/verification_anchors.json` outside the
generation path.

The closure leg on every row pins that `parse(render(x))` is total: the fuzzer
found that `fromString("10E2147483647")` succeeded while its rendering
`"+1.0E+2147483648"` (adjusted exponent int32 max + 1) was rejected by the
parser's own old literal-must-fit-int32 rule, identically in all seven
consumers. The exponent rule is final-value-based exactly so that every
rendered adjusted-exponent literal (at most int32 max + 33, far below the
shared `2^53` literal bound) reparses to the same `Components`.

## Payload Scope

The standalone BID codec `Components` payload represents the full BID128 110-bit
NaN payload, subject to the schema-wide value limit of `10^33` (the widest
canonical BID128 NaN payload, mirroring the coefficient's `10^34-1` schema cap).
BID32/BID64 NaN payloads are unaffected subsets of the same field.

A payload value below `10^33` — including values at or above 2^64 — is a valid
`Components` encode input in every required language (decode preserves the full
payload, encode splits it back into the low word and the high-word payload
field), and the canonical high-payload anchor vector round-trips bit-exactly.
Whether a raw BID128 NaN bit pattern is a canonical vector stays a
whole-encoding property: re-encoding the decoded components must reproduce
every input bit, including the reserved combination bits, so a random NaN
pattern with an in-range payload is usually still noncanonical. A payload at or
above `10^33` remains noncanonical decode-only input whose decode normalizes
the payload to 0, the same boundary the `encode` reject contract enforces
(`payload_overflow`) and the `fromString` grammar enforces
(`nan_payload_exceeds_schema_max`).

Each language expresses the payload in the form symmetric with its coefficient:
Go `*big.Int` (nil = the declared default zero payload), Rust `u128`, Java
`BigInteger` (null = zero), Python `int`, JavaScript/TypeScript `bigint`, and
Swift a `payloadHi`/`payloadLo` `UInt64` pair. The unsigned fixed-width
representations (Rust, Swift) enforce the `10^33` value limit through validation,
matching how their `u128`/`UInt64`-pair coefficient already enforces `10^34-1`.

## Source of Truth

`devtools/cmd/testgen` generates vectors from the standalone BID bit-layout reference codec in `devtools/internal/testgen` and the
seed/count configuration in `devtools/testgen_manifest.json`. It does not import the production
`bid754-codec-go` package as an oracle.

The same generator produces the Go, Rust, Java, Python, JavaScript/TypeScript,
and Swift consumer harnesses. `make verify-generated` regenerates and compares
the vectors and consumer harnesses together.
