# bid754 Rust Crate

`bid754` is bid754's public Rust implementation: an IEEE 754-2019 decimal
floating-point (BID encoding) library generated from the Go mechanical port
of Intel BID C. The public API — value types, operation wrappers, and
associated constants — is generated by a dedicated `devtools/tools/go2rs`
pass (`apiemit`), not hand-written; see `docs/ARCHITECTURE_SPEC.md` and
`docs/SPEC.md` for why the implementation and its public entrypoints are
both generated artifacts rather than hand-maintained glue.

**Publish status:** the crate still carries `publish = false` in
`Cargo.toml`. It is not yet on crates.io. Lifting `publish = false`, bumping
to a first published version, and running `cargo publish` are a separate,
explicitly user-approved step; `make verify-rust-package` (from the
repository root) is the package-shape gate that runs ahead of that step
today. Until then, consume this crate from a repository checkout (a `path`
dependency, or a `git` dependency pinned to a commit).

## Public API

The generated public API surface covers fixed-width `Decimal32`,
`Decimal64`, and `Decimal128` value types with 379 parity-verified wrapper
methods/constructors and 12 associated constants
across the three widths (`devtools/generated/testspec/rust_api_surface_inventory.json`
is the generated machine-readable Go-symbol-to-Rust-symbol map; the
repository-level `rust_public_api_parity_wrappers`/`rust_public_api_constants_total`
anchors in `devtools/verification_anchors.json` pin those two counts).

- **Value types** — `Decimal32(u32)`, `Decimal64(u64)`, `Decimal128([u8; 16])`,
  each `#[repr(transparent)]` with a compile-time size assertion and no
  backend pointer or extra metadata: the Rust type's memory layout is exactly
  its BID bit pattern. `from_bits`/`to_bits` (32/64) and
  `from_le_bytes`/`to_le_bytes` (128) are the raw bit-pattern accessors.
  `Binary128` is the analogous fixed-width wrapper for `to_binary128`'s IEEE
  binary128 result.
- **Parse** — `parse(&str) -> Result<Self, ParseDecimalError>` and
  `impl FromStr` require an exact, complete literal and reject finite
  inexact/overflow/underflow results. `parse_with_flags(&str) ->
  Result<(Self, ExceptionFlags), ParseDecimalError>` and `parse_with_mode`
  expose rounded finite results and flags. `parse_raw(&str) -> (Self,
  ExceptionFlags)` routes valid finite/infinity input through the Intel port and
  retains its result and flags. Malformed syntax, or a written cohort whose quantum or
  coefficient Intel would silently change with zero status, is rejected through
  the public failure channel: the `Result` APIs return an error and `parse_raw`
  returns canonical quiet NaN plus `INVALID_OPERATION`. Explicitly flagged
  overflow/underflow/inexact results retain the Intel result and flags on the
  flag-returning APIs. The internal generated readtest path, not the public raw
  parser, preserves Intel's malformed-text fall-through for native comparison. A
  representable NaN literal (`"NaN42"`, `"-SNaN"`, ...) is constructed directly
  from the public grammar; a payload too large for the target width returns
  canonical quiet NaN plus `INVALID_OPERATION` on the raw flag channel and is
  an error on the `Result` APIs.
- **Arithmetic and transcendental-adjacent ops** — `add`/`sub`/`mul`/`div`
  (ties-to-even default) plus `*_with_flags` pairs, `fma`, `sqrt`,
  `remainder`, `fmod`, `quantize`/`quantize_with_flags`,
  `min_num`/`max_num`/`min_num_mag`/`max_num_mag`,
  and the seven `round_integral_*` variants. Intel's Tier 1 D/Q mixed-width
  arithmetic is exposed with an explicit rounding mode: Decimal64 has
  `{add,sub,mul,div}_{dq,qd,qq}_with_mode`, and Decimal128 has
  `{add,sub,mul,div}_{dd,dq,qd}_with_mode`. Intel's mixed-width fused and
  square-root extensions are exposed without compositional widening or
  narrowing: Decimal64 has
  `fma_{ddq,dqd,dqq,qdd,qdq,qqd,qqq}_with_mode` and `sqrt_q_with_mode`, while
  Decimal128 has `fma_{ddd,ddq,dqd,dqq,qdd,qdq,qqd}_with_mode` and
  `sqrt_d_with_mode`.
- **Comparison** — `quiet_eq`/`quiet_lt`/`quiet_le`/... and
  `signaling_eq`/`signaling_lt`/... pairs returning `(bool, ExceptionFlags)`,
  plus `total_cmp`/`total_cmp_mag -> core::cmp::Ordering`. `==`, `<`, and `>`
  are also available directly through `impl PartialEq` / `impl PartialOrd`
  (quiet semantics, matching the `f64` precedent: a NaN is unordered and
  unequal to everything including itself, `-0 == +0`, and the types are
  therefore deliberately not `Eq`/`Hash` — use `to_bits()`/`to_le_bytes()` or
  `total_cmp` for bit-identity comparison, a total order, or hash-map keys).
- **Predicates and introspection** — `is_zero`/`is_nan`/`is_infinite`/
  `is_normal`/`is_finite`/`is_subnormal`/`is_signaling`/`is_canonical`/
  `is_sign_negative`, `sign`, `class() -> DecimalClass`, `same_quantum`, and
  the `RADIX: u32` associated constant.
- **Other IEEE operations** — `logb`/`ilogb`/`scaleb` (exponent manipulation;
  `ilogb` is the integer-`logBFormat` form and returns
  `(i64, ExceptionFlags)`, signalling invalid operation with `i32::MAX` for an
  infinite operand and `i32::MIN` for a zero or NaN operand),
  `next_up`/`next_down`/`next_toward` (the IEEE nextUp/nextDown/nextAfter
  family), `abs`/`neg`/`copysign` (sign manipulation).
- **Conversions** — `to_i8..to_i64`/`to_u8..to_u64` and their `_exact`
  siblings (all take a `RoundingMode` and return `(_, ExceptionFlags)`),
  `to_f32`/`to_f64`/`to_binary128` (mode-taking), and `to_decimalN`
  cross-width conversions (widening — e.g. `Decimal32::to_decimal64` — takes
  no rounding mode, since it is always exact; narrowing — e.g.
  `Decimal64::to_decimal32` — takes a `RoundingMode`), plus `impl From<i32>`/
  `impl From<u32>` (`Decimal64`/`Decimal128`) and `impl From<i64>`/
  `impl From<u64>` (`Decimal128` only) for the integer conversions that are
  exact for the full source range — narrower exact ranges (e.g. `Decimal32`
  from `i32`/`u32`) stay explicit `from_iN`/`from_uN` methods with a
  rounding mode instead of an infallible `From`, since they are not exact
  for the full range. The `DecimalN::from_int` convenience constructors use
  nearest-even conversion but accept only exact results: `Decimal32` and
  `Decimal64` return `Err(InexactIntegerError)` when the source integer is not
  exactly representable, while every `i64` is exactly representable by
  `Decimal128`.
- **Display** — `impl Display` (`to_string()`; both use the same
  scientific-style `[sign] coefficient E [sign] exponent` rendering as the Go
  `String()` port output, e.g. `"+7E+0"`, not a "natural" decimal-point
  form).
- **Associated constants** — `ZERO`/`ONE`/`PI`/`E` per width, computed at
  generation time by an independent BID interchange-format encoder (not the
  runtime string parser) and cross-checked by the public API parity gate
  against a fresh parse of their documented decimal literal.
- **`RoundingMode`** — a closed 5-variant enum (`NearestEven`, `NearestAway`,
  `TowardZero`, `TowardPositive`, `TowardNegative`); an invalid discriminant
  is not constructible (`TryFrom<u32>` returns `Result` for the fallible
  integer-to-mode path). This is the Rust-native counterpart of the Go
  `RoundingMode`-is-an-open-`int` invalid-mode flag path: the Rust type
  system rules the invalid case out entirely instead of raising a flag at
  runtime.
- **`ExceptionFlags`** — an 8-flag bit set (`INEXACT`, `UNDERFLOW`,
  `OVERFLOW`, `DIVISION_BY_ZERO`, `INVALID_OPERATION`, `SUBNORMAL`,
  `ROUNDED`, `CLAMPED`) with `contains`/`is_empty`/`Display` (the same
  `"Inexact|Overflow"`-style vocabulary as the Go public API).
- **`Context`** — an explicit `{ rounding: RoundingMode, flags: ExceptionFlags }`
  pair (also `Default`, equivalent to `Context::new()`) with `set_flag`/
  `clear_flag`/`has_flag`/`clear_all_flags`/`save_all_flags`/`restore_flags`
  (IEEE 754-2019 5.7.4 vocabulary) and the per-width `add32`/`add64`/`add128`
  context-driven operations. No heap or pointer indirection (flag
  accumulation is through `&mut self`), unlike the Go `ArithmeticContext`;
  and no nil-context default either, since Rust has no implicit global
  rounding setting for a method to fall back to — the mode always comes
  from `self.rounding`.
- The public API module (`src/generated/api/`) is `#![forbid(unsafe_code)]`
  and denies `arithmetic_overflow`/`overflowing_literals`; wrapper bodies
  only call into `crate::generated::*` port functions, convert value types,
  and map exception flags, never reproducing arithmetic.

Not provided, by design: a global mutable default-rounding setter (the Go
`SetDefaultRounding`/`DefaultArithmeticContext` pair — implicit global state
is deliberately not part of this API; use `Context::with_rounding` instead),
the Go convenience surface `AddSlice*`/`IsValidDecimalString`/
`GetRequiredPrecision`, and `std::ops` operator traits (`Add`, `Neg`, ...) —
those are outside the current declared generated surface. The inventory entry
for every mapped-vs-excluded Go symbol
(including why each of these was left out) is
`devtools/generated/testspec/public_api_routing_inventory.json`
(Go census) and `devtools/generated/testspec/rust_api_surface_inventory.json`
(the Go-to-Rust symbol map).

```rust
use bid754::{Decimal64, ExceptionFlags, RoundingMode};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let a: Decimal64 = "1.5".parse()?;
    let b = Decimal64::from_int(2)?;
    let sum = a.add(b); // ties-to-even, matching the IEEE default
    assert_eq!(sum.to_string(), "+35E-1"); // BID scientific-style rendering, see Display below

    let (rounded, flags) = a.round_integral_exact_with_flags();
    assert_eq!(rounded.to_string(), "+2E+0");
    assert!(flags.contains(ExceptionFlags::INEXACT));
    let (toward_zero, flags) = a.round_integral_exact_with_mode(RoundingMode::TowardZero);
    assert_eq!(toward_zero.to_string(), "+1E+0");
    assert!(flags.contains(ExceptionFlags::INEXACT));
    Ok(())
}
```

`RoundingMode::NearestDown` and `BID_ROUNDING_NEAREST_DOWN` are non-IEEE
decTest compatibility values. They exist only in the `#[doc(hidden)]`
internal compatibility modules below (`gen_constants`) for generated/internal
verification plumbing; the public `RoundingMode` enum never includes them, so
the type itself defines the boundary without a separate adapter.

## Non-Stable Internal Modules

Beyond the public API surface above, this crate also exposes a handful of
`#[doc(hidden)]` modules for repository integration tests, benchmarks, and
generated verification harnesses:

- `generated`: Go-to-Rust generated BID implementation functions (what the
  public API wrappers call into)
- `gen_types` and `gen_constants`: generated Intel BID compatibility types
  and constants
- `tables`: generated table compatibility layer
- `bid_codec`: repository-local BID component encode/decode helpers used by
  vectors

These modules are not a semver contract. Do not depend on them; use the
public API surface described above instead.

The standalone public BID codec package is `../bid754-codec-rs`; it has its
own package metadata, README, lockfile, and generated cross-language vector
tests.

## `no_std`

This crate is `std`-only for the v0.2 line: the generated implementation and
the public API (`parse`/`Display`/error types) use `String`/`Vec`/`format!`
and `std::error::Error`. `no_std` support is a separate future project, not
part of the current generated surface (`docs/ARCHITECTURE_SPEC.md`).

## Verification

From the repository root:

```sh
make test-rust
make test-bid-string
make test-bidcodec
make verify-rust-package
```

`make test-rust` (`cargo test --locked` in this crate) runs the fixed-vector
codec/string tests, the **public API parity gate**
(`tests/public_parity_generated.rs`: every one of the 379 wrapper symbols,
bit-compared against an independent direct call into the same
`crate::generated::*` port function the wrapper itself calls, with the
flag/rounding mapping re-derived from independent numeric literals so a
shared-converter bug stays visible), and the **Rust decTest portable leg**
(`tests/dectest_generated.rs`: the same IBM decTest suites the Go mechanical
port cross-checks, run against the generated Rust engine, value + quantum +
5-flag parity). Both are generated by `devtools/cmd/testgen`, not
hand-maintained. `make verify-rust-package` is the package-shape gate: a
closed-set `cargo package --list` file check (only `src/**`, `LICENSE`,
`NOTICE`, `README.md`, `Cargo.toml`, plus Cargo's own bookkeeping files ship)
and a `[dependencies]` pin/FFI-absence check.

The FFI verification harness against the Intel BID C oracle lives in the
repo-internal `ffi-verify/` crate (`bid754-ffi-verify`, `publish = false`),
so this crate carries no FFI dependency. With native Intel BID prerequisites
present, the generated readtest runner (561 dispatched functions, 0 skips)
is `make test-rust-native` from the repository root, and the optional
randomized Rust vs C fuzz complement can be run with:

```sh
cd bid754-rs/ffi-verify
cargo test --locked --features ffi-fuzz --test fuzz_vs_c
```

That `ffi-fuzz` path compares result bits and `_IDEC_flags` for selected
arithmetic functions, but it is not the regular generated FFI bit-compare
profile.
